# `attachments_upload` — how to use it from another process

Module: `scripts/teams_agent/attachments_upload.py`
Public API: `upload_and_send(chat_name, file_path, text="", conv_id=None, timeout_s=60.0) -> str | None`

---

## Minimal integration

```python
from pathlib import Path
import sys

sys.path.insert(0, str(Path(__file__).resolve().parents[2] / "scripts" / "teams_agent"))
from attachments_upload import upload_and_send

msg_id = upload_and_send(
    chat_name="Notes",              # substring of the chat's name in the rail
    file_path=Path("/tmp/report.md"),
    text="Weekly report",           # optional note (markdown OK)
    conv_id="48:notes",             # optional: skips the REST lookup
    timeout_s=60.0,                 # optional: how long to wait for the verify step
)
if msg_id:
    print(f"OK, message {msg_id}")
else:
    print("Upload failed")
```

## Environment requirements

The process needs access to:

1. **`session.json`** in `scripts/teams_agent/` — the Teams session (gitignored, regenerated by `login.py`).
2. **`.auth-token`** in the same folder — the Bearer token for the chatsvc REST verify step.
3. **Playwright + Chromium**: `python -m playwright install chromium` once.
4. Packages: `playwright`, `requests` (already in the repo).

## Important notes

### 1. Conflict with the Bob daemon

`cli.py` keeps its own Playwright instance from `session.json`. A second process running `upload_and_send` at the same time **opens a separate Chromium** — that is fine, but:

- Both read the same `session.json` (read-only, so it is safe).
- `.auth-token` is a cache file (cli.py writes it from the token interceptor, the upload reads it). A fresh token is enough.
- Without a live Bob session (`cli.py` running) `.auth-token` can expire (~1 h). The upload refreshes it from a chatsvc call along the way, but if the REST `find_conversation_id` is the first call it may get a 401. It is safer to **pass `conv_id` explicitly** (skips the REST lookup):

```python
upload_and_send("does-not-matter", path, conv_id="19:00000000000000000000000000000000@thread.v2")
```

### 2. Cost

~5–8 s per call: launch Chromium (1 s) + Teams shell (3 s) + chat switch (1 s) + CDP drop + Enter + verify (~3 s). **Do not call it per message** — only when you really want to upload a file. For bulk work, build a wrapper that reuses one Playwright session.

### 3. 512 KB limit

Hard-coded `_MAX_UPLOAD_BYTES`. Change it if you plan larger files, but files larger than 1–2 MB should go through a chunked upload (`createUploadSession`) — a CDP drag is not enough then.

### 4. Rename on conflict

SharePoint returns `name "report.md"` on the 1st upload, `"report 1.md"` on the 2nd, `"report 2.md"` on the 3rd — `?@name.conflictBehavior=rename` is hard-coded in the sniffed URL. If you want an overwrite or unique names with a prefix, set `file_path.name` with a timestamp before the call.

## Typical scenarios

### A) MCP tool / cron / scheduler

A short-lived, ad-hoc process:

```python
result = upload_and_send("Notes", report_path, conv_id="48:notes")
if not result:
    raise RuntimeError("upload failed — check session.json + .auth-token")
```

### B) Long-running service

`upload_and_send` launches and closes Playwright on every call. It is a simple but slow model. If you call it more than once a minute, write a wrapper that keeps `browser`/`context` alive between calls (keep `page.goto(TEAMS_URL)` as a warm-up once at start).

### C) The Bob daemon (`cli.py`)

It can call it directly, but:

- the daemon already has an open Playwright session, so spawning a second one costs an extra Chromium process
- a better route: add an "upload a file" mode to `ai.py` as a tool (Claude calls `upload_attachment`, cli.py uses the existing `page` instead of a new one)

## Diagnosing failures

The `[upload]` lines on stderr show where it broke:

| Message | What it means | Fix |
|-----------|-----------|-----|
| `ERROR: file does not exist` | bad path | check `file_path` |
| `ERROR: file X B > limit` | > 512 KB | change the limit or split the file |
| `ERROR: conv_id not found` | the REST lookup did not find the chat | pass `conv_id` explicitly |
| `ERROR: could not open the chat` | the switch in the rail did not find it | use a more unique substring, or sign in to Teams by hand and check the chat is in Favorites / visible |
| `ERROR: composer did not mount` | the DOM took long to render (slow disk / cold start) | try again; if it keeps happening, raise the `wait_for_selector` timeout (around line 228) |
| `ERROR: REST did not confirm` | the drop happened, but the message did not appear | check in Teams by hand; Teams may be blocking it, or `.auth-token` may have expired |

Older builds print the same lines with `BLAD:` and Polish text.

## About session.json

If the session expires (typically after a few days without Bob running), the upload returns `ERROR: could not open the chat` or stops on the Microsoft sign-in screen. **Refresh it**:

```bash
python3 scripts/teams_agent/login.py
```

This opens Teams web interactively and Playwright saves the session.

## Sanity test before using it for real

```bash
python3 scripts/teams_agent/attachments_upload.py /tmp/test.md \
    --chat "Notes" --conv-id "48:notes" --text "smoke test"
```

If it returns `OK msg_id=...`, it is ready to be used from another process.

## How it works underneath (TL;DR)

1. Playwright headless Chromium from `session.json`.
2. `page.goto("https://teams.microsoft.com/v2/")` + `scraper.switch_to_chat_by_name(page, chat_name)` switches to the target chat.
3. **CDP `Input.dispatchDragEvent`** delivers the file to the composer. This is the key part: an ordinary JS-synthesised `DragEvent` with a `DataTransfer` has `isTrusted=false` and Teams rejects it. A CDP-level event passed through Chromium has `isTrusted=true` — Teams treats it exactly like a real drag-and-drop from the desktop.
4. `Enter` in the composer: Teams sends the message with `properties.files` after uploading to SharePoint first (Chromium handles the whole OAuth handshake itself).
5. Polling chatsvc REST (`api_client.get_messages`) checks that a message with `sequence_id > baseline` really appeared with the attachment. Without this a silent failure (a block on the Teams side, a network error) would look like success.

### Why not REST only

A direct PUT to `/_api/v2.0/drive/root:/<folder>/<file>:/content` does not work: SharePoint rejects it (401/403) without the Teams Web Client's full OAuth handshake (POST `_layouts/15/filebrowser.aspx?app=TeamsFile` + POST `_api/SP.OAuth.NativeClient/Authenticate`). Recreating that in plain Python is hours of work, which is why the module uses a browser.
